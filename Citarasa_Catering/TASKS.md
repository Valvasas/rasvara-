# Daftar Tugas — Citarasa Catering

Backlog perbaikan & pengembangan lanjutan, dikelompokkan per area. Ini bukan daftar statis — tambah/coret/pindahkan item seiring berjalannya proyek. Beri tanda `[x]` saat selesai, jangan hapus item lama begitu saja (biar ada jejak keputusan); pindahkan ke bagian "Selesai" jika daftar aktif mulai penuh.

Cara pakai: sebelum mulai kerja, cek dulu apakah tugas terkait sudah ada di sini. Sebelum menutup sesi kerja, perbarui status di sini.

## Sedang berjalan — persiapan rilis ke client

Fase 1 (kematangan tampilan & kepercayaan) dan fase 2 (voucher & peta) sudah selesai; sisanya:

- [ ] **Rahasia produksi dirotasi di sisi server (hanya bisa dikerjakan pemilik/admin server)** — `.env` dan `.env.production` di repo sudah diisi nilai baru pada 2026-09-20, tetapi nilai lama sempat ikut terbagikan bersama folder proyek. Yang masih harus dilakukan di server: pakai sandi database baru saat membuat database, dan isi `SEED_TELEPON_PEMILIK` dengan nomor pemilik yang sebenarnya (`node scripts/verify-production.mjs` sengaja masih GAGAL sampai nomor itu diisi).
- [ ] **Monitoring error terpusat (Sentry/APM)** — belum ada; lihat bagian "Fitur bisnis masa depan".
- [ ] **Perlindungan anti-bot pada formulir pesanan** — pembeli tamu tidak perlu login dan nomor HP tidak diverifikasi. Batas laju per-IP (10 pesanan/menit) dan batas ukuran input sudah ada, tetapi belum ada CAPTCHA (mis. Cloudflare Turnstile) maupun verifikasi OTP. Pertimbangkan bila mulai ada pesanan palsu.
- [ ] **Lupa sandi (reset tanpa login)** — ganti sandi saat login sudah ada (lihat bagian Selesai), tetapi pengguna yang lupa sandinya belum punya jalur pemulihan; butuh OTP WhatsApp/SMS. Sesi *pelanggan* juga belum bisa dicabut dari server (sesi pemilik/staf sudah).

- [ ] **Payment gateway (Midtrans Snap, sandbox dulu)** — butuh akun merchant terverifikasi milik pemilik usaha, jadi hanya bisa sampai tahap sandbox dari sisi pengembangan. Webhook cukup memanggil `catatPembayaranInti` (invarian #3: satu pembayaran = satu baris kas) dan harus idempotent per ID transaksi gateway.
- [ ] **Jeda minimum pesanan hari-H** — saat ini pesanan untuk hari ini hanya ditolak bila jamnya sudah lewat. Perlu keputusan pemilik: berapa jam minimum dapur butuh persiapan (mis. 3 jam) sebelum jam acara.
- [ ] **Batas pemakaian voucher per pelanggan** — sekarang kuota bersifat global. Bila nanti perlu "satu kali per nomor HP", tambahkan tabel pemakaian voucher per pelanggan; jangan andalkan kuota global.

- [ ] **Singgahan pengaturan per proses** — `ambilPengaturan()` menyimpan singgahan 60 detik di memori proses. Di PM2 cluster/beberapa kontainer, perubahan pengaturan baru terlihat di proses lain setelah ≤ 60 detik. Tidak berbahaya untuk tampilan; jalur yang menyangkut uang/otomasi sudah membaca langsung dari DB. Bila nanti horizontal scaling serius, pindahkan ke `revalidateTag` atau Redis.
- [ ] **Audit dependensi transitif** — `mysql2`/`deepmerge-ts` (Prisma CLI) dan `uuid` (exceljs) masih dilaporkan `npm audit`; tidak terjangkau saat runtime (lihat DEPLOYMENT.md §7). Periksa ulang tiap rilis Prisma/exceljs.
- [ ] **Stok bahan (gudang)** — sengaja belum: resep + harga bahan sudah memberi daftar belanja & HPP. Stok butuh disiplin input harian; tambahkan hanya bila pemilik siap mencatat pemakaian.

## Fitur bisnis masa depan (tahap lanjutan)

- [ ] **Verifikasi pembayaran otomatis (Payment Gateway)** — saat ini pembeli mengunggah bukti transfer lalu pemilik verifikasi manual di kanban. Integrasi payment gateway (mis. Midtrans / Xendit) bisa mengotomatiskan ini, tetapi pakai jalur `catatPembayaranInti` yang sudah ada (invarian #3 di AGENTS.md).
- [ ] **Integrasi WhatsApp Business API resmi** — saat ini tombol chat membuka tautan `wa.me` langsung. Penggunaan WhatsApp Cloud API dapat mengirim pesan notifikasi otomatis saat dapur memperbarui status pesanan.
- [ ] **Multi-cabang / multi-outlet** — skema saat ini eksplisit single-tenant UMKM (`Pengaturan` baris tunggal `id: "utama"`). Jika usaha ingin ekspansi membuka cabang baru, ini membutuhkan perubahan skema multi-cabang.
- [ ] **Monitoring & Sentry di produksi** — integrasi Sentry / APM untuk menangkap error runtime di sisi klien maupun Server Actions secara terpusat.

- [x] **Pengerasan kesiapan produksi (audit pra-rilis)** — sembilan perbaikan, semuanya diverifikasi dengan server berjalan (`typecheck`, `lint`, 81 test, `build`, plus uji HTTP langsung):
  1. **Bukti transfer tidak lagi terbuka untuk umum.** Berkas unggahan pindah dari `public/unggahan/` ke `DIREKTORI_UNGGAHAN` (bawaan `data/unggahan`) dan dilayani `src/app/unggahan/[nama]/route.ts`. Foto menu (`menu-*`) tetap publik dengan cache satu tahun; bukti transfer (`bukti-*`) hanya untuk pemilik/staf dapur, pembeli yang nomornya cocok, atau tamu yang memegang cookie `pesanan_saya` bertanda tangan — sisanya 404 dengan `private, no-store`. Diuji: cookie tamu dipalsu → 404, cookie untuk pesanan lain → 404, pelanggan lain yang login → 404, nama berkas di luar pola & path traversal → 404. Kolom `buktiBayarUrl` diberi indeks (migrasi `20260920000000_indeks_bukti_bayar`) karena route ini mencarinya pada setiap permintaan gambar.
  2. **Unggah foto dari ponsel tidak lagi gagal.** Batas bawaan Server Action adalah 1 MB, sementara validasi aplikasi mengizinkan 5 MB — jadi hampir semua foto kamera ditolak Next.js sebelum sempat divalidasi. `experimental.serverActions.bodySizeLimit` disetel `6mb`; diverifikasi dengan unggahan 7 MB yang kini ditolak dengan pesan "Body exceeded 6mb limit".
  3. **Dua test yang gagal diperbaiki.** `tests/auth.test.ts` gagal karena `lib/db.ts` membuka koneksi saat modul diimpor, sehingga setiap test yang menyentuh `lib/auth.ts` menuntut `DATABASE_URL` walau tidak pernah menyentuh database; klien sekarang dibuat saat kueri pertama. Ekspektasi sanitasi CSV di `tests/keamanan.test.ts` memang keliru (menuntut spasi yang tidak pernah ditulis kodenya). 81 test lulus.
  4. **Kondisi balapan di papan dapur ditutup.** `aksiPindahStatus` dan `aksiTandaiLunas` dulu membaca pesanan di luar transaksi; dua orang yang menekan tombol bersamaan sama-sama lolos pemeriksaan. Keduanya kini memakai kunci optimistis di dalam transaksi, pola yang sama dengan kuota voucher. Ini yang menjaga invarian #3 saat tombol "Tandai Lunas" diklik dua kali.
  5. **Batas ukuran input pesanan.** Server Action bisa dipanggil tanpa lewat formulir; nama, alamat, catatan, jumlah item, dan kuantitas kini dibatasi. Ditambah: pesanan "diantar" wajib beralamat minimal 10 karakter — sebelumnya alamat kosong bisa lolos ke dapur.
  6. **Rahasia dibersihkan.** `docker-compose.prod.yml` tidak lagi memuat sandi database bawaan (kini `${POSTGRES_PASSWORD:?}`), `.gitignore` diperbaiki karena pola lamanya tidak mencakup `.env.production`, dan kunci sesi dibuat ulang — kunci dev dan produksi sekarang berbeda.
  7. **Backup menyertakan berkas unggahan.** Isi folder unggahan tidak ada di database, jadi cadangan lama akan memulihkan pesanan dengan semua tautan gambar rusak. Skrip juga kini membaca `.env.production`, bukan hanya `.env` — cron di server sebelumnya berjalan tanpa `DATABASE_URL`.
  8. **CI disamakan dengan produksi.** Node 20 → 24 (sama dengan Dockerfile), dan `npm run lint` ikut dijalankan.
  9. **Operasional.** `HEALTHCHECK` di Dockerfile, Nginx tidak lagi menimpa `Cache-Control` di `/unggahan/` (yang akan membuat bukti transfer tersimpan di cache bersama), dan `verify-production.mjs` menambah pemeriksaan nomor pemilik, `SEED_DEMO`, serta `POSTGRES_PASSWORD` (2026-09-20).
