# Daftar Tugas — Citarasa Catering

Backlog perbaikan & pengembangan lanjutan, dikelompokkan per area. Ini bukan daftar statis — tambah/coret/pindahkan item seiring berjalannya proyek. Beri tanda `[x]` saat selesai, jangan hapus item lama begitu saja (biar ada jejak keputusan); pindahkan ke bagian "Selesai" jika daftar aktif mulai penuh.

Cara pakai: sebelum mulai kerja, cek dulu apakah tugas terkait sudah ada di sini. Sebelum menutup sesi kerja, perbarui status di sini.

## Sedang berjalan — persiapan rilis ke client

Fase 1 (kematangan tampilan & kepercayaan) dan fase 2 (voucher & peta) sudah selesai; sisanya:

- [ ] **Payment gateway (Midtrans Snap, sandbox dulu)** — butuh akun merchant terverifikasi milik pemilik usaha, jadi hanya bisa sampai tahap sandbox dari sisi pengembangan. Alur `StatusBayar` wajib dijaga: satu pesanan tetap maksimal satu `CatatanKas` (invarian #3), dan webhook harus idempotent.
- [ ] **Jeda minimum pesanan hari-H** — saat ini pesanan untuk hari ini hanya ditolak bila jamnya sudah lewat. Perlu keputusan pemilik: berapa jam minimum dapur butuh persiapan (mis. 3 jam) sebelum jam acara.
- [ ] **Batas pemakaian voucher per pelanggan** — sekarang kuota bersifat global. Bila nanti perlu "satu kali per nomor HP", tambahkan tabel pemakaian voucher per pelanggan; jangan andalkan kuota global.

## Fitur bisnis masa depan (tahap lanjutan)

- [ ] **Verifikasi pembayaran otomatis (Payment Gateway)** — saat ini pembeli mengunggah bukti transfer lalu pemilik verifikasi manual di kanban. Integrasi payment gateway (mis. Midtrans / Xendit) bisa mengotomatiskan ini, tetapi alur `StatusBayar` harus dijaga dengan hati-hati (lihat invarian #3 di AGENTS.md — satu pesanan tetap harus maks satu `CatatanKas`).
- [ ] **Integrasi WhatsApp Business API resmi** — saat ini tombol chat membuka tautan `wa.me` langsung. Penggunaan WhatsApp Cloud API dapat mengirim pesan notifikasi otomatis saat dapur memperbarui status pesanan.
- [ ] **Multi-cabang / multi-outlet** — skema saat ini eksplisit single-tenant UMKM (`Pengaturan` baris tunggal `id: "utama"`). Jika usaha ingin ekspansi membuka cabang baru, ini membutuhkan perubahan skema multi-cabang.
- [ ] **Monitoring & Sentry di produksi** — integrasi Sentry / APM untuk menangkap error runtime di sisi klien maupun Server Actions secara terpusat.

## Selesai

- [x] **Sistem voucher / kode promo** — model `Voucher` (potongan rupiah atau persen, batas potongan maksimal, minimal belanja, kuota, masa berlaku) dengan pengelolaan di `/admin/voucher`. Aturannya ditulis sebagai fungsi murni di `src/lib/voucher.ts` supaya dipakai bersama oleh pratinjau di formulir dan perhitungan final di server — keduanya tidak mungkin berbeda. Potongan selalu dihitung ulang dari database saat pesanan dibuat (invarian #1); browser hanya mengirim kodenya. Kuota diamankan dengan kunci optimistis (`updateMany` bersyarat `terpakai`) supaya dua pemesan yang menekan kirim bersamaan tidak sama-sama memakai kuota terakhir. Potongan hanya memakan harga hidangan, tidak pernah ongkos antar. Kode voucher di-snapshot di pesanan (invarian #2) dan voucher yang pernah dipakai hanya dinonaktifkan, tidak dihapus. 12 unit test di `tests/voucher.test.ts`; diuji end-to-end sampai memastikan angka di layar sama persis dengan yang tersimpan di database dan kuota naik tepat satu (2026-09-16).
- [x] **Peta titik antar (Leaflet + OpenStreetMap)** — pembeli menandai lokasi pengantaran di peta, koordinat disimpan di `Pesanan`, dan kartu dapur menampilkan tautan yang membuka titik itu di aplikasi peta ponsel pengantar. Sengaja **tidak** memakai Google Maps JS API: itu menuntut akun penagihan dan biaya per pemuatan peta, sementara navigasi pengantar tetap memakai aplikasi Google Maps miliknya sendiri lewat tautan koordinat — hasil sama, biaya nol. Peta dimuat dengan `next/dynamic` dan hanya saat pembeli memilih diantar, karena membuka peta berarti mengirim IP pembeli ke server ubin pihak ketiga. Alamat tertulis tetap wajib, jadi peta murni pelengkap dan pembeli yang memakai pembaca layar atau menolak izin lokasi tetap bisa memesan (2026-09-16).
- [x] **Kebijakan privasi & S&K diperbarui mengikuti fitur baru** — bagian 2b menjelaskan koordinat lokasi dan hubungan ke OpenStreetMap; ringkasan di atas halaman ikut dikoreksi karena klaim "tidak dibagikan ke siapa pun" tidak lagi tepat begitu peta ada. S&K mendapat bagian 3b tentang aturan voucher (2026-09-16).
- [x] **Galeri multi-foto per menu (gaya e-commerce)** — model `FotoMenu` (maksimal 5 foto per menu, foto urutan 0 jadi sampul), unggah/hapus/jadikan-sampul di `/admin/menu` lewat `KelolaFotoMenu.tsx`, dan komponen `GaleriFotoMenu.tsx` di halaman detail dengan geser jari (CSS scroll-snap, tanpa pustaka carousel), tombol maju/mundur, strip thumbnail, dan indikator "n / total". Tanpa putar-otomatis karena merampas kendali pembaca layar. Kartu menu menampilkan lencana jumlah foto. Sebelumnya kolom `fotoUrl` ada di skema tetapi **tidak ada cara mengisinya sama sekali** dari dashboard, sehingga seluruh katalog tampil sebagai ikon kategori (2026-09-16).
- [x] **Metadata produksi & pratinjau WhatsApp** — `layout.tsx` sebelumnya menunjuk `/favicon.ico` yang berkasnya tidak pernah ada (tab browser kosong). Kini favicon, apple-icon, dan gambar Open Graph dihasilkan dari kode lewat `ImageResponse`, ditambah `metadataBase`, tag Open Graph + Twitter Card, `robots.ts`, `sitemap.ts` (ikut memetakan tiap halaman menu), dan manifest PWA. Tanpa ini, tautan yang dibagikan di grup WhatsApp — jalur masuk utama pembeli UMKM — hanya muncul sebagai URL polos tanpa gambar maupun judul (2026-09-16).
- [x] **Halaman kebijakan privasi & syarat-ketentuan** — ditulis sesuai perilaku sistem yang sebenarnya (data yang benar-benar disimpan, dua cookie yang benar-benar dipakai beserta umurnya, hak pengguna menurut UU PDP No. 27/2022), bukan templat umum. Tertaut di kaki halaman (2026-09-16).
- [x] **Halaman performa website (`/admin/analitik`)** — statistik kunjungan harian, halaman terpopuler, dan corong pemesanan. Pelacakan **tanpa cookie**: pengunjung unik dihitung dari SHA-256 atas (IP + user agent + garam harian acak yang tidak pernah disimpan), sehingga sidik tidak bisa dibalik menjadi IP dan tidak bisa dihubungkan antar hari — inilah alasan situs ini tidak memerlukan banner persetujuan cookie. Semua data teragregasi per hari sejak ditulis, dan path bertanda identitas (`/pesanan/:kode`) disamarkan sebelum disimpan (diuji di `tests/analitik.test.ts`). Warna grafik dipilih lewat pengujian keterbacaan buta warna: pasangan bata+daun hanya berjarak ΔE 7 pada deuteranopia, diganti bata-tua+kunyit dengan ΔE 20 (2026-09-16).
- [x] **Perbaikan penanggalan WIB di formulir pemesanan** — `minTanggal` memakai `toISOString()` yang berbasis UTC, sehingga antara pukul 00.00–07.00 WIB tanggal minimum mundur sehari dan pembeli dini hari melihat tanggal kemarin (melanggar invarian #4). Ditambah penolakan jam acara yang sudah lewat untuk pesanan hari ini — sebelumnya pesanan pukul 08.00 masih bisa masuk pada pukul 20.00. Batas jam operasional sengaja **tidak** dipakai untuk membatasi jam antar, karena `jamBuka`/`jamTutup` adalah jam layanan dan pesanan pagi memang lazim dimasak dini hari (2026-09-16).
- [x] **Perbaikan migrasi database awal yang hilang (bug kritikal deploy)** — folder migrasi `20260913000000_struktur_awal` yang disebut di ARCHITECTURE.md ternyata tidak pernah ter-commit ke repo; hanya migrasi susulan `tambah_peran_staf_dapur` yang ada, dan itu menjalankan `ALTER TYPE` pada enum `Peran` yang belum pernah dibuat. Akibatnya `npm run db:deploy` selalu gagal total di database baru (clone baru, staging, CI, produksi) — proyek tidak bisa dijalankan dari nol. Migrasi baseline dibuat ulang dari `prisma/schema.prisma` (via `prisma migrate diff --from-empty`) dan ditaruh dengan timestamp sebelum migrasi staf dapur agar urutan riwayat tetap logis. Diverifikasi: `db:deploy` dari database kosong sukses, `db:seed` sukses, `typecheck`/`lint`/`test` (41 test)/`build` semua lolos bersih, dan aplikasi dites langsung di browser pada halaman toko & admin (2026-09-15).
